**Bounded GO for the anchor half, not engine selection or production readiness.**
At `89ae3a0ab8d941a2885e6ec89d094bc9ce9d2922`, the required ordering seam

## Interface and maintenance surface

`anchors.patch` adds only `ListOpLog::insertion_spans_at(&self, frontier: &[LV])
-> Vec<(DTRange, bool)>` in `src/listmerge/merge.rs`. Each tuple contains a
local insertion-ID range and its visibility at that cut, in native CRDT order.
Deleted insertions remain present. Delete-operation IDs and insertions not yet
born at the cut are absent. Span segmentation and LVs are not portable; existing
agent assignment converts ranges to remote `(agent name, sequence)` identities.

Implementation:

1. Call the existing `Graph::make_m1_plan` from root to the queried frontier with
   `allow_ff = false`.
2. Exhaust the existing `TransformedOpsIterRaw::from_plan`, which uses the
   unmodified `M2Tracker`, `CRDTSpan`, index and range tree.
3. Scan the native range tree, exclude the underwater sentinel, and expose
   `span.id` and `!span.end_state_ever_deleted`.

No order is independently computed. There is no actor-sort workaround,
transformed numeric cursor, canonical replay, duplicate merger or separate
tombstone structure in the implementation. Test-only sorting compares ID sets,
not CRDT order; test-only native-patch projection independently checks visible IDs.

Two internal invariants become maintenance obligations: disabling fast-forward
must retain insertion identities/tombstones, and the exhausted root-to-cut plan's
**end** state represents the union of that cut's causal closure. Its current
state can be the last visited branch, so using `current_state` would be wrong.
The generated tests compare full tombstone order across arrival orders, not just
converged text. These tests must follow any upstream planner/tracker change.
This is bounded evidence, not a general tombstone-order convergence proof.

## Cursor semantics exercised by the test adapter

The native addition is an ordering interface, not a serialized cursor type.
The small test-only adapter stores `Start`, `End`, or one remote insertion ID
with `Before`/`After`. It has no saved numeric position or creation frontier.

- Left affinity selects the visible left neighbor with `After`, or `Start`.
- Right affinity selects the visible right neighbor with `Before`, or `End`.
- Resolution counts visible scalars preceding that **native identity boundary**.
  If the primary is deleted, before and after collapse together, but other
  insertions retain their native ordering relative to that tombstone.
- An unknown ID, missing sequence, delete-operation ID, or insertion whose birth
  is absent from the target cut returns `None`. Unrelated creation-time history
  is not required. Historical queries are checkouts, not merges into the tip.
- Root/edge sentinels mean unconditional document start/end, even when created
  at a later empty cut. Thus no primary birth is required for sentinels.

These are not Loro labels or a promise to reproduce the old numeric affinity
policy. For example, after deleting a run and inserting a replacement at its
collapsed visible position, DT orders the replacement before the retained
tombstones. Both sides of those deleted IDs then resolve after the replacement.
The repeated-Unicode test records the concrete result `3`, rather than silently
assuming the old numeric position `1`. A product cursor policy must accept these
identity-boundary semantics or explicitly specify another policy before binding.

## Limits and next decisions

Each query costs a full native root-to-cut merge plus a span scan and allocates
the plan, tracker and result vector. The test adapter expands scalar IDs and
rebuilds per call; neither is a per-keystroke implementation or a performance
measurement. Batching/caching would need separately measured design work.
Frontiers must be valid and history retained, as for checkout; this addition
is not an untrusted-input validator or a panic/resource bound. The exercised
profile uses native forward inserts and forward/reverse deletes; manually
flipped reverse-insert runs are already unimplemented in the native tracker.

No native field or byte-format extension is needed. Remaining work is to
maintain/review the tiny internal seam, accept/specify the cursor policy, and
qualify performance, compatibility and platforms before any permanent binding.
No upstream contact, publication, commits, I03 work, engine selection,
independent review, Windows/WSL run or whole-workspace validation occurred here.
